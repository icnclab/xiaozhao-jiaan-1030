# GitHub：核准隔離分支同步與手動 Drive 交付

本次新增 `tools/approved_sync/scripts/publish_approved_branch.py`，沿用既有不可變 Git blob 匯出、敏感規則及逐檔 hash 審核表，不碰應用服務／資料庫。不自動 Commit、掃描整個主目錄或切換任何來源分支；不匯入或呼叫 Drive／OAuth 程式。

## 核准佇列，不依賴 dirty 主目錄

排程的輸入是本機受控 registry，每筆明確指定：`repoPath`（隔離 clone／worktree）、`sourceBranch`、完整 `approvedCommit`、精確 `stableTag`、已審核遠端基底 `reviewedBaseRef`／`reviewedBaseCommit`。另以 `protectedRepo` 禁止主工作目錄成為來源。設定不放機密；只有完成審核與測試後，維護者才登錄 pin，不自動猜測新 HEAD 已核准。

```json
{
  "enabled": false,
  "protectedRepo": "C:/aa/ltc_care_installer_20260912/ltc_care",
  "jobs": []
}
```

以上為停用範例，不能把任意工作目錄加入佇列。正式啟用的本機設定與排程 action／回復備份存於主目錄下 `run/approved-github-sync/`，不進 Git；以本機驗證結果為準。每日排程是否切換成功須實際讀回 action；不能因工具寫好就宣稱已啟用。

## 每筆必要條件

1. 實驗室 GitHub 使用者 `icnclab`、精確私人 origin；registry 明確啟用且非空。
2. 來源不是 protected 主工作區；分支與 HEAD 與 pin 一致；tracked clean。untracked 不會自動加入，也不會匯出。
3. `stable-ready-*` 輕量標記直接指向核准 SHA；不以任意名稱或 moving branch 取代。
4. 已審核基底仍對應指定遠端 SHA，且為此 commit 祖先。receipt 的 backend／typescript／frontend／sensitiveReview 全 PASS，sourceDigest 與實際來源相同。receipt 不是代跑測試，必須由完成測試與審核者提供；變更來源即失效。
5. 逐一掃描基底後所有新增 commit，不只看最後 diff；即使秘密後來刪掉，新增歷史仍拒絕。新增非白名單路徑（除了必要 receipt）拒絕；不能把資料目錄、訪談、憑證偷偷帶入歷史。
6. 匯出整份來源再次掃描並產出四份交付檔。若既有檔案不同，不覆寫；同版相同內容可重用。
7. 只寫 `sync/approved-<SHA前12碼>` 與指定穩定 tag，不寫 main 或舊穩定分支。目標若已指其他 SHA 就停止；不用 force，branch＋tag 以 atomic push 一次提交，不半套成功。
8. push 後重新用 ls-remote 核對 branch **及** tag 都是完整核准 SHA，才記成功。遠端本已一致記 verified_existing，不能說本次新推送；網路或 SHA 不一致即阻擋。

## 結果與排程

- `pushed_verified`：真正推送後雙 ref 核對一致，remoteVerified=true。
- `verified_existing`：遠端原已一致且重新核對，remoteVerified=true；不重傳。
- `skip`：dirty、換分支／HEAD、停用或空佇列，remoteVerified=false，exit **2**。
- `blocked`：掃描／權限／來源／歷史／receipt／遠端衝突／驗證失敗，remoteVerified=false，exit **1**。
- `--check-only` 會做驗證及本機包，不推送，remoteVerified=false，exit 2；不能當 GitHub 備份完成。

本機 `github-approved-sync.jsonl` 記 UTC、完整 SHA、分支／tag、ZIP SHA256、結果與手動 Drive 狀態，不印命令 stderr／秘密。排他鎖不會因時間過久而自動刪除；殘留鎖需人工確認。單筆阻擋即停止本輪，不自動重試 push；下次只核對明確核准的 pin，遇衝突仍拒絕，不換分支繞過。

本次優先沿用既有每日 `XiaoZhao-GitHubSyncDaily`，只調整 GitHub action，保留時間、帳號與其餘設定；不另建 Drive 排程。SessionEnd 舊腳本保持原樣，仍可能對主目錄 dirty SKIP，不能將其訊息混同新版每日結果。不啟動原舊同步程式，避免它的測試讀取主目錄設定。

### 後續新穩定版本

在隔離工作區逐檔審核、完成實際測試與掃描 → 提交對應 sourceDigest 的 receipt → 通過原 pre-commit hook 提交 → 建立精確 stable-ready tag → 將完整 SHA、分支、tag 與可信遠端基底登錄本機 registry。來源 HEAD 後來改變就會 SKIP，必須重新審核 pin，不會自動 Commit 或把新修改加入備份。

不要讓被核准的來源工作區承擔持續未提交開發；需要繼續開發時保留另一個乾淨隔離來源，或等下一次穩定後再更新 pin。主工作目錄的 167 筆不需處理，也不因排程被加入 Git。

## 手動 Drive 與 LM

每個 SHA 專屬目錄產出 ZIP、`.zip.sha256`、VERSION 與 LM 四個檔案。只提醒本人以實驗室帳號網頁上傳 `XiaoZhao/ApprovedSource`；不啟動 API、OAuth、Console、Drive Desktop 或 OneDrive。Google 備份完成狀態分開記錄，不因 GitHub 成功而改成 Drive 成功。

原穩定版 78ff63e90412：本人已回報四檔上傳，狀態為 **已上傳、尚未重新下載驗證 SHA256**。不能設 cloudVerified=true。新版本仍是待本人手動上傳。

## 回復

調整排程前保留原 task XML、SHA256 及 action 備份。若新版有問題，可將 registry enabled 設 false 停止 GitHub 寫入，再依備份恢復既有 task action；不刪備份、不恢復資料庫、不變更服務。舊 action 恢復後主目錄 dirty 仍會 SKIP，須誠實回報，不能稱恢復了成功備份。
