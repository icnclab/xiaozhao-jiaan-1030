# 小照／嘉安專題：Claude Code 開發規範與工具運作說明

> 本文件整理自專案的 `CLAUDE.md` 與 `.claude/skills/` 下的 Skill 定義，目的是給 Google NotebookLM
> 之類的學習工具使用，方便之後的開發者快速理解「這個專案怎麼跟 Claude Code 協作」。
> 已移除帳號密碼、Token、個資與不必要的內部環境細節（例如實際機器路徑、IP、帳號名稱），
> 只保留技術重點與流程。

## 1. 小照的開發規範

### 1.1 專題背景與範圍
- 「小照」是長照 AI 助手系統，依據一次正式訪談（嘉安機構第二次照服員訪談）的需求開發。
- 新需求必須先列出根據（哪次會議、哪項訪談紀錄），不自行擴充產品範圍。
- AI 的角色是輔助，**不取代醫療判斷、急救或緊急聯絡（119/110）**。
- 每次工作要產生「可驗證的新進度」，禁止把重跑已經通過的測試當成新進度。

### 1.2 指令與回報的固定格式
每次具體操作指令建議固定分三段說明：
1. **現在執行**什麼。
2. **成功後**要做什麼（下一步、如何驗證）。
3. **失敗後**要做什麼（如何還原、要回報什麼資訊）。

並明確標出：
- 執行的環境（例如實驗室主機 vs. 個人電腦）。
- 使用的終端類型（PowerShell、SSH 等）。
- 成功的判斷標準。
- 是否需要還原機制。

### 1.3 嚴格區分「驗收階段」
說明任何進度時，必須清楚區分下列五個不同等級，不能混用：
1. 程式已寫好（code written）。
2. 離線測試通過（單元測試、不連資料庫的 Mock 測試）。
3. 已部署（程式碼已經放到實際執行環境）。
4. HTTP 層驗收（打 API 確認回應正確）。
5. 真人操作驗收（實際使用者操作過，不是模擬）。

**只做到 import 成功或 build 成功，不能宣稱「已上線」或「已完成真人驗收」。**

### 1.4 工作環境慣例
- 後端：Python + FastAPI，虛擬環境獨立於專案內。
- 前端：TypeScript + Vite + LINE LIFF。
- 本機 API 預設埠號、健康檢查端點（`/api/healthz`）、正式資料庫名稱，都已在設定檔集中管理，不應該寫死在程式各處。
- 遠端連線一律透過已授權的機制（如 Tailscale），**不自行開放公網連接埠或變更防火牆設定**。
- GitHub 使用私人 repository；**禁止自動 push、禁止 `git add .`／`git add -A`**，只能用明確檔案清單加入版本控制。

### 1.5 正式環境安全規範（最核心的一組規則）
- 動手前先 `git status`、比對實際程式與資料庫結構，擬出**最小修改範圍**。
- 修改資料庫前要先有可核對的備份或還原機制；資料庫更新一律加條件限制，並驗證「實際被影響的列數」。
- **絕對禁止**：刪庫、`DROP`、`TRUNCATE`、危險的重置操作、跨機構解除權限、未授權資料匯出、把真實個案資料寫入測試。
- 高風險變更（會影響正式服務或資料的）必須先完整展示修改內容與影響範圍，取得明確同意才執行，避免「無人值守」狀態下自動進行。
- **不讀取、不輸出、不上傳**：環境變數檔、金鑰、Token、密碼、真實病歷、個案紀錄、機構內部機密；任何診斷紀錄輸出前要先移除敏感值。
- 任何法規或服務項目的來源資料，要確認原始出處、版本、生效日是否一致；不可自行把「尚待審核（reviewed/approve）」的狀態改成「已核准」。
- 測試一定要有具體的成功輸出（像是測試通過筆數、HTTP 狀態碼），光是「程式碼能被 import」不算驗收完成。

### 1.6 額度與執行效率
- 預設使用效能/成本平衡的模型，只有遇到真正複雜的問題才切換到更高成本的模型。
- 先讀取真正相關的少量檔案，避免整個專案地毯式搜尋或重複讀取大型檔案。
- 一次只修改真正需要改的檔案，不要順手做無關的整理。
- 長任務適時做上下文整理（避免對話記憶爆掉）；新主題開新的工作階段，不要把不相關的任務疊在一起。
- 如果 AI 工具的使用額度不足，應該提供「可以直接在終端機執行、不依賴 AI 持續在線」的獨立指令，讓人可以自己繼續做。
- 每批工作結束前更新工作紀錄：已完成什麼、還有什麼待驗證、卡在哪裡、下一步是什麼。

## 2. 四個 Skill 的用途、觸發條件與執行流程

> Skill 是一組「寫好的操作手冊」，讓 Claude Code 在特定情境下，照著已經驗證過的固定步驟做事，
> 而不是每次都重新想一遍流程。本專案目前有四個 Skill（原文件稱「三個」，第四個
> `github-sync` 是後來新增的 GitHub 同步流程）。

### 2.1 `fieldtest-validation`：47 人場測驗證

**用途**：確保場測儀表板（管理員專用）的帳號查詢、編號對應（照服員 A01–A40、居督 S01–S07）、
統計、Excel 匯出四個環節都正常、都限管理員存取、而且不會洩漏姓名或問答內容。

**觸發條件**：
- 修改了場測相關的後端路由、前端儀表板頁面，或場測參與者資料表的 Migration。
- 有人問「場測可以開始了嗎」「場測資料會不會洩漏個資」。

**執行流程**：
1. 跑後端「純邏輯測試」：直接匯入測試模組執行（不透過 pytest、不連資料庫），檢查編號規則（A 開頭限照服員、S 開頭限居督）、管理員限定、跨機構隔離、資料表不存在時要回傳清楚的錯誤（不是裸露的伺服器錯誤）。
2. 跑前端「真實 DOM 操作測試」（用模擬瀏覽器環境實際填表單、按按鈕），確認空位不會被誤判成「已完成」、查無帳號時訊息清楚。
3. 跑整套前端測試＋型別檢查，確認沒有連帶弄壞其他畫面。
4. 若需要連線真正的資料庫才能確認「資料表到底建好了沒」，**這一步不屬於本 Skill 可自動完成的範圍**，必須明確回報需要管理者在隔離測試環境核可後才能驗證。

**驗證標準**：上述測試全部通過；人工核對 Excel 匯出欄位清單，確保沒有任何會洩漏個資或問答內容的欄位。

**停止條件**：資料表還沒建立、需要真實資料庫連線才能完整驗證、或發現任何洩漏個資的跡象時，都要停下來回報，不自己執行 Migration、不略過風險繼續宣稱驗證通過。

### 2.2 `ltc-safety-review`：角色權限與個案資料安全審查

**用途**：確保「照服員／居督／主任／管理員」四種角色，前端看得到、改得到的範圍跟後端實際授權邏輯一致；確保個案資料不會跨機構外洩；確保高風險問題（緊急狀況、用藥、補助金額等）一定轉人工處理，不由 AI 直接回答。

**觸發條件**：
- 修改了角色權限相關的後端程式（角色常數、登入授權邏輯）或風險規則判斷邏輯。
- 修改了前端依角色顯示選單／按鈕的邏輯。
- 有人問「這樣改會不會讓不該看的人看到個案」。

**執行流程**：
1. 先用 `git diff` 列出這次改動實際影響哪些角色、哪些 API 端點，比對後端角色常數跟前端選單隱藏清單是否一致（例如：後端只給某角色唯讀權限，前端就不該出現該角色操作不了的按鈕）。
2. 跑前端角色相關測試（用模擬 API，不連真實資料庫）。
3. 跑後端權限邏輯的純邏輯測試（直接匯入測試模組執行），確認「非該角色就該被拒絕」「不同機構查不到對方資料」的斷言成立。
4. 確認高風險規則（緊急、用藥、補助金額等關鍵字）能正確攔截問題並轉人工。
5. 若需要真實資料庫才能完整驗證跨機構存取，要明確記錄「這部分需要資料庫連線＋授權」，不自己連線；若之前已經用示範帳號驗證過，要註明是哪一輪、用什麼帳號。

**驗證標準**：前端測試全部通過；確認未授權呼叫會被拒絕、跨機構查詢查不到對方資料，而且這些判斷發生在任何資料庫寫入動作之前。

**停止條件**：發現前端跟後端權限不一致時，要修正前端去配合後端（不是放寬後端配合前端）；需要放寬某角色權限才能讓功能動起來時，要停下來列出需要授權的具體範圍，交由管理者決定；需要用真實個案資料才能驗證時，只能改用虛構資料。

### 2.3 `rag-evaluation`：RAG 問答鏈路驗證

**用途**：確保「提問 → 檢索 → 證據篩選 → 風險規則 → 回答或轉人工 → 引用出處」這條完整鏈路，在修改檢索/問答相關程式後仍然完整、仍然安全——不會亂答、不會漏判高風險、不會假裝有出處其實沒有。

**觸發條件**：
- 修改了檢索、證據篩選、風險規則、問題理解、逐字稿處理、嵌入向量 provider、文件服務等任一相關程式。
- 有人問「RAG 還正常嗎」「這次改動會不會斷鏈」。
- 要調整嵌入模型或向量維度。

**執行流程**：
1. 先用 `git diff` 看清楚改了什麼；如果牽動到嵌入向量的維度或模型，這會連動資料庫的向量欄位，屬於需要正式 Migration 才能生效的高風險變更，**不能只靠這個 Skill 驗證完就直接套用**。
2. 跑純邏輯測試（不連資料庫，一定要先做這一步）。
3. 做模組載入檢查，確認程式至少能被正確匯入（用假的資料庫連線字串，不需要真的連得上）。
4. 如果有獨立的「示範環境」在跑（連的是示範用資料庫，不是正式資料庫），可以用已知的示範帳號做一次端對端測試：問一題跟示範文件內容相關的問題，確認有正確回答與出處；再問一題明顯無關的問題，確認會轉人工而不是亂答。這一步**不能用在正式 API** 上，而且示範環境沒在跑就不能假裝測過。

**驗證標準**：上述指令全部成功執行、沒有拋出例外；若用了示範環境驗證，「有回答」要有正確出處，「轉人工」且沒有引用出處也算正確行為（代表證據不足時的安全預設），不是缺陷。

**停止條件**：牽動嵌入維度或模型（需要正式 Migration）時要列出需求但不自行執行；純邏輯測試任何一項失敗時要先修正（判斷是程式錯還是測試過時），不能略過；需要連線正式資料庫或正式 API 才能驗證時要明確回報，不自己連線。

### 2.4 `github-sync`：GitHub 安全同步流程

**用途**：確保每次要把本機程式同步到私人 GitHub repository 時，都走同一套「檢查 → 測試 → 敏感資訊掃描 → Commit → Push 新分支 → 遠端確認」流程，而不是隨意推送。

**背景限制**：
- GitHub 上的 `main` 分支跟本機完整開發歷史是兩條完全獨立的歷史（沒有共同祖先），因此同步一律推到新分支，不直接動 `main`。
- 本機工作目錄通常同時存在「真正要同步的程式」跟一堆不該同步的東西（編輯過程留下的備份檔、來源不明的壓縮檔、正式環境的 SQL 修補或資料庫備份還原紀錄、真實訪談逐字稿、展示用錄音文件、金鑰檔）。只有第一類該進 GitHub，其餘要加進 `.gitignore`，但**不刪除原始檔案**。

**固定流程**：
1. **檢查修改**：確認 Git 狀態、遠端設定、本機與遠端歷史的關係；逐一分類未追蹤檔案。
2. **測試**（必須真的執行、看到實際通過的結果，不能只憑「程式能被匯入」就宣稱通過）：後端完整測試、前端型別檢查、前端完整測試。任何一項失敗就停止，不降低標準讓測試勉強通過。
3. **敏感資訊掃描**：對「這次真正要加入版本控制的內容」做模式比對（常見的金鑰格式、私鑰標頭、聊天機器人權杖、帶密碼的資料庫連線字串等）；如果是第一次推送某批新 commit，要額外對整個歷史掃一次。掃到任何可疑內容就停下來回報，不自行決定要不要推送。
4. **Commit**：用明確列出的檔案清單加入版本控制，**不使用** `git add .` 或 `git add -A`。Commit 動作會自動觸發本機的 Git Hook（見下一節），任何一步沒過就會中止 Commit。
5. **Push**：永遠推到新分支，不直接對 `main` 操作；不使用強制推送、不重置歷史、不刪除遠端分支。
6. **遠端確認**：比對本機與遠端的 commit 雜湊值，必須完全一致才算同步成功。
7. **切換分支時的保護機制**：如果同步前目前分支上有未提交的修改，不要直接用 `git checkout <其他分支>`（這會讓 Git 把工作目錄「安全地」還原成目標分支的舊內容，看起來像修改消失，其實是因為該修改已經在別的分支被提交過，Git 認定可以覆蓋）。需要同時保留兩邊未提交狀態時，要用「從新分支取出內容到工作目錄、再取消暫存」的方式，並在切換前後都用 `git status` 確認未提交檔案數量沒有變少。

**停止條件**：沒有 repository 存取權限、掃到可疑的金鑰或密碼、遠端歷史跟本機不同且必須靠合併或強制推送處理、任何一項測試失敗且無法在安全範圍內修正。

**已建立的自動化（供理解現況，細節可能隨時間調整）**：
- 有兩個觸發點會自動執行同一支本機同步檢查腳本：Claude Code 工作階段結束時的 Hook，以及每天固定時間、僅限本機已登入時執行的工作排程器。兩者共用同一支腳本與同一個鎖檔，避免互相搶跑。
- 自動化**不會**自己判斷「這次改動算不算穩定」，也不會自動 Commit。要讓某個 commit 被自動同步，必須明確在該 commit 上打一個特定格式的 Git 標籤，而且工作目錄裡已追蹤的檔案不能有未提交修改。符合條件時，自動化才會依照上面的固定流程（抓遠端、確認還沒同步過、敏感資訊掃描、跑測試、全過才推送、推送後再次核對遠端）執行；任何一步沒過就只留紀錄，不會重試、不會自己放寬標準。
- 自動化**不會**：自動 Commit、自動打標籤、強制推送、對 `main` 動手、推送沒打過標籤的 commit；排程只在主機開機且使用者已登入時才會跑，不會補跑離線期間錯過的次數。

## 3. Harness（Claude Code 執行環境）的測試與 Git Commit 流程

### 3.1 本機 Git Hook：Commit 前的輕量級檢查
專案設定了一個 Commit 前（pre-commit）的檢查腳本，**只做不需要連線資料庫的檢查**：
1. 一批已經確認「不會連資料庫」的後端純邏輯／Mock 測試，用直接匯入模組執行的方式跑（不是透過完整的測試框架），刻意繞開會連資料庫的測試設定檔。
2. 前端 TypeScript 型別檢查。
3. 前端完整測試（全部用模擬環境／假的瀏覽器環境，不連真實資料庫）。

**這個腳本絕對不會做**：連線資料庫、執行資料庫 Migration、部署正式環境、推送到 GitHub、發送真實的訊息通知。任何一步檢查沒通過，Commit 就會被中止。

這個檢查腳本本身會被版本控制保存，但 Git 預設不會自動套用它，每台電腦複製專案後要自己手動設定一次才會生效（這個設定只存在於本機的 Git 設定裡，不會被提交，也不會影響其他專案）。

### 3.2 一般開發的測試標準
- **後端**：優先使用完整測試框架執行完整測試（可以連接測試用資料庫，跟正式資料庫完全分開）。某些 Skill 流程裡提到的「純邏輯測試」是刻意設計成不連資料庫的子集，用於快速檢查，但不能取代完整測試。
- **前端**：TypeScript 型別檢查 + 完整測試（使用模擬瀏覽器環境），兩者都要通過。
- **測試結果一定要有具體輸出**（通過的測試數量、exit code），不能只憑「程式碼能被成功匯入」就宣稱測試通過。
- 測試失敗時要先分析、修正根本原因，不可以透過放寬測試標準、刪減測試內容或跳過失敗測試的方式讓測試「看起來」通過。

### 3.3 Commit 與 Push 的紀律
- 加入版本控制一律使用「明確列出每個檔案路徑」的方式，不使用會把整個工作目錄不分青紅皂白加入的指令。
- Commit 前要先確認這次改動的範圍跟目的單一、清楚；Commit 訊息要說明「為什麼」而不是單純重複程式碼變更的內容。
- Push 永遠推到獨立的功能分支，不直接對正式穩定分支或 `main` 操作；不使用強制推送、不重置歷史。
- 任何牽涉到正式服務、正式資料庫的高風險操作，要先完整展示修改內容與影響範圍，取得明確同意才執行。

## 4. 各項工具如何協助小照專題開發

### 4.1 Skill（技能手冊）
Skill 把「已經驗證過、特定情境該怎麼做」的固定流程寫成文件，讓後續每次遇到同樣情境時，都照著同一套已知安全、已知有效的步驟執行，而不是每次重新摸索。本專案的四個 Skill（場測驗證、角色權限安全審查、RAG 鏈路驗證、GitHub 同步）分別對應專題裡四類最容易出錯、也最需要一致把關的工作。

### 4.2 具備讀寫能力的檔案工具
用於直接讀取、搜尋、修改程式碼與設定檔，取代「複製貼上整份檔案內容」的笨方法：
- 精確搜尋程式碼裡的特定字串或模式（例如找出所有用到某個角色常數的地方）。
- 用「找出要改的這一段、換成新的這一段」的方式修改檔案，而不是整份覆寫，降低改錯無關內容的風險。
- 依檔名規則找出符合條件的檔案（例如找出所有測試檔）。

### 4.3 終端指令執行工具
用於實際執行後端測試、前端建置與測試、Git 操作、資料庫唯讀查詢等。專案要求任何會影響正式服務或資料庫的操作，執行前要先列出具體指令、預期結果與回復方式，不能憑空執行。

### 4.4 背景與平行工作機制
對於「研究型」或「不需要把過程細節留在對話裡」的工作（例如大範圍搜尋、長時間執行的測試），可以用獨立的子任務處理，只把最終結論帶回主要對話，避免把大量中間過程塞進同一個對話裡。

### 4.5 持久化記憶機制
用於記錄「使用者是誰、偏好怎樣的協作方式、這個專案目前在忙什麼、過去踩過哪些坑」，讓下一次開新的工作階段時，不需要重新解釋一次背景。記憶內容會刻意排除「看程式碼就能知道的事」（例如架構、檔案位置），只保留真正需要額外說明、容易遺忘的脈絡。

### 4.6 使用者澄清機制
當任務裡有真正需要使用者本人決定的分岔點（例如兩種做法各有取捨、需要授權才能繼續），會直接提出具體選項讓使用者選擇，而不是自己猜測後直接動手，也不是每個小細節都要確認而拖慢進度。

### 4.7 排程與自動化機制
用於建立「每天固定時間檢查一次」或「某個條件達成時才觸發」的重複性工作（例如 GitHub 同步自動化），讓例行檢查不需要每次都靠人手動啟動，同時保留明確的停止條件與安全邊界，避免在無人確認的情況下做出高風險動作。
