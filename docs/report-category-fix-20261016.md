# 分類回報檢查與最小修正

## 已確認的程式證據

- `frontend/src/liff/pages/ReportPage.tsx` 從 `/api/categories` 取得分類及內含的 `templates`，沒有另一個常見問題載入 API。有資料時原本就會逐項顯示按鈕；空陣列時原本留白。
- `backend/app/api/caregiver_routes.py:list_categories` 僅回傳登入者機構、啟用分類，以及該分類的啟用模板。沒有從知識庫自動產生常見問題的流程。
- `tools/clean_db.py` 只建立分類及預設督導，明確不建立示範模板。這能解釋使用該初始化資料時沒有問題按鈕，但不能證明正式資料庫目前沒有管理員另外建立的模板。本次未執行此工具。
- 換分類時原本保留上一分類模板 ID；後端會因模板不屬於分類而拒絕。現已清除選取。
- 建案 API 會核對分類機構、模板分類，使用 client_request_id 防重複，並於 commit 後回傳案件。成功回傳並不代表督導已讀。
- 督導列表限制 Case.org_id，詳情與回覆使用 `_org_case` 核對機構；回覆儲存後建立通知工作。建立案件本身沒有寄送督導 LINE 通知的呼叫，不應承諾督導已收到通知。
- 督導列表預設顯示待處理與處理中；「只看指派給我」、搜尋及測試帳號預設隱藏也可能讓既有案件不顯示。不是所有未顯示都代表建案失敗。
- 本機 frontend/dist 既有檔案日期為 2026-10-12；包含「已送交督導確認」，未找到「已送出，等待回覆」。無法確認使用者當時連到的版本或瀏覽器快取。

## 修改內容、依據、測試、副作用

1. ReportPage：加入分類載入／空分類／空模板提示，換分類清除模板。依據為上述 render 與選取流程；隔離測試覆蓋有資料、無資料與換分類。沒有新增正式常見問題。
2. ReportPage：成功顯示「案件已建立」、回傳案號與狀態，說明尚不能證明督導已讀；送出錯誤改為結果未確認，提供我的案件連結並維持原 request ID 重試。依據為 commit 與網路回應可能中斷的時間差；測試覆蓋成功、失敗及重試。副作用是提示文字改變，API 合約不變。
3. frontend/tests/report.test.tsx：新增 6 項測試，所有 API 均 mock、只使用測試文字。6/6 通過；前端整套 98/98 通過，`npx.cmd tsc --noEmit` 通過。未載入 backend pytest fixtures。測試未證明正式案件或 LINE 通知成功。
4. 本文件：保留判斷依據及未確認事項，不改動正式資料。驗證方式為與實際讀取的程式對照。

## 仍需唯讀核對（不要為核對而新增或修改資料）

1. 以原使用者正常登入，開啟「我的案件」，尋找原測試案件，記下案號、分類、狀態、負責督導及既有回覆。不要貼出姓名、Token 或個資。
2. 以同機構督導登入後台，清空搜尋、取消「只看指派給我」、選「全部」狀態。若原使用者為 test_ 帳號，勾選顯示測試案件。用同一案號核對詳情與既有回覆。沒有回覆時不能聲稱回覆流程已實測成功；新增回覆會寫正式資料，不屬本次唯讀核對。
3. 由管理員唯讀查看「分類與常見問題」：該分類是否有啟用模板。亦可在瀏覽器開發工具查看已登入頁面原本發出的 `/api/categories` 回應，只核對該分類的 templates 是否為空；不要分享授權標頭。
4. 若後台有啟用模板而同機構 API 未回傳，需進一步在安全離線快照核對分類 ID、啟用狀態和機構，不直接連正式資料庫。若 API 有回傳、畫面沒有，記錄當時前端檔案版本與瀏覽器錯誤，不據此新增模板。

## 部署

本次只修改前端原始碼，未覆寫正在使用的 frontend/dist，未重啟服務。正式套用需要重新編譯並部署前端；API 與 Worker 無需因本修正重啟。登入、綁定與後端機構權限程式未修改。正式資料、知識庫、Gold、RAG、安全規則及 Failure Type 均未修改。
