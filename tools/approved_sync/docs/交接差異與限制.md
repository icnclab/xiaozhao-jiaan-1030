# 交接差異與限制（2026-11-08）

## A. GitHub `main` vs 穩定版

1. 使用者提供的 `xiaozhao-jiaan-1030-main(1).zip` **只有初始骨架**。其中的 README 自己寫明：「不是完整的小照後端，也不是可直接在新電腦執行的完整專案」。
2. `.github/workflows/offline-tests.yml` 要求 `requirements-test.txt` 和 `backend/app/` 模組，但此 ZIP 沒有這些目標，因此單靠 `main` 不能執行該工作流程。
3. 歷史 Codex/Claude 紀錄稱 `sync/stable-20261107-jiaan1030` 分支已 Push 完整程式（Commit `139887e60ebd9db1cdaea21a0c021931daeb822c`），後續另有公開端點與 Token 安全修正分支。必須以 STUST 上的 `git ls-remote`、`git status`、`git log` 實際重新比對，不能假定 `main` 是最新，亦不能把不同分支的程式混在一起覆蓋。
4. 歷史曾有把未提交檔案切分支後意外還原，再修復的紀錄，因此建議使用獨立 clone/worktree，**只比較，不直接在正式工作目錄切分支**。

## C. 導入要求

- 不覆蓋目前的 `backend/app/` 與 LIFF 介面，先比對路由、資料契約、資料庫 Schema、執行緒與呼叫順序。
- 先以 **UAT feature flag** 關閉預設導入；離線測試、UAT mock 試用、對比基準（多人意圖正確率、P0 漏判率、誤報率、P50/P95 延遲）通過後才能考慮正式整合。
- P0 風險仍依現有人工督導與緊急 SOP，不可讓 `mpc_core.py` 的關鍵字規則單獨決定是否需要通知。
- 新 LINE 官方帳號「小照 UAT 測試機器人」的 `uat.local.env` 只留在 STUST 本機；需確認 UAT 不誤用正式 `ltc_clean`、正式 LINE 及 Funnel Webhook。
- 新架構或知識更新後，只產出**不含個資的 LM 學習摘要**，提示使用者依既有 LM 規則處理。

## D. 雙雲端同步設計

- **來源真相**：實驗室 STUST 原始程式 → 程式碼／測試／敏感資訊審核 → GitHub 私人穩定分支 → **同一 Commit** 的篩選程式 ZIP → 實驗室 Google Drive。
- `scripts/sync_verified.py` 可在穩定標記存在且目前 GitHub 同步腳本允許時，呼叫既有 `github_sync_check.ps1`（不是自行 git add/commit），然後只讀確認遠端 GitHub SHA，匯出白名單程式碼 ZIP。
- 每 15 分鐘檢查**已發布**的新版本；無更新時不產生重複 ZIP。對剛存檔尚未提交、未審核或測試不過的程式，不自動分享。
- Google Drive for desktop 的同步狀態在客戶端或雲端網站再核對；本工具包不能單靠本機檔案存在就保證雲端完成。
- 執行紀錄保存在 `%LOCALAPPDATA%\XiaoZhaoSync\logs\dual_sync.jsonl`，不含密碼與 Token。
